01LLM 调用基础

📘 知识点
  • 调用本质：消息列表进 → 文本出。三种角色：system（规则）/ user（输入）/ assistant（模型说过的话，多轮必须带上才有记忆）
  • temperature：随机性旋钮；token：计费与理解的最小单位；上下文窗口：一次能塞的记忆上限
  • 最重要的认知：输出是概率性的——同输入不保证同输出，承诺的格式也不总兑现
⚠️ 注意事项
  • 用户输入永远不要拼进 system——system 是规则层，user 是数据层，混了就是注入漏洞
  • 调试期固定 temperature；采样参数要随调用日志落库——复现某次调用时缺了参数就不算完整证据
  • 记录每次的 usage，成本意识从第一天开始；对模型输出永远保留校验这一步
llm-unify contracts.py：七字段统一协议（案例未落库采样参数，列为已知差距）

02记忆与上下文管理

📘 知识点
  • 短期记忆 = 消息列表的累积：对话历史、工具结果全都追加进上下文；上限是窗口，计量是 token——记忆是有成本的
  • 三个管理手段：裁剪（只留最近 N 轮）、摘要（旧历史压缩成梗概保留）、外置（存向量库、用时检索——即 RAG，检索增强生成）
  • 一个比喻：上下文窗口是内存，向量库是硬盘——内存贵而快容量小，硬盘大而便宜，聪明的 Agent 分层使用
⚠️ 注意事项
  • 别等窗口报错才处理——接近上限就要有裁剪/摘要策略（超窗异常是最后防线不是设计）
  • 工具结果直接喂回会快速膨胀上下文——长输出先摘要再入列
  • 历史消息也是"发生过的事"：被污染过的轮次要能标记与剔除；RAG 检索回来的内容同样不可信（间接注入的入口之一）
  • 多轮 assistant 历史必须带上，否则模型每轮"失忆重来"
llm-unify 已实现超窗异常识别＋自动换更大窗口路由；事前裁剪/摘要在案例中留作练习，RAG 属进阶篇

03统一调用层（多供应商）

📘 知识点
  • 各家 API 协议互不兼容：system 位置、鉴权头、字段名、流式事件、错误格式全都不同
  • 解法：防腐层——定义自己的统一接口（各家的公共交集），每家写一个适配器做翻译
  • 判断标准：业务代码里搜不到别人家的字段名（instructions、x-api-key…）
⚠️ 注意事项
  • SDK 自带的重试要显式关掉（如 OpenAI SDK 默认 max_retries=2）——多层重试相乘，流量放大 27 倍的事故就是这么来的
  • 换模型前先想好路由与降级：主力模型挂了谁顶上？
  • 密钥走环境变量，永远不进代码库（.env 加入 gitignore）
  • 留一个"无 Key 演示模式"，评审和测试都省事
llm-unify 三适配器 + ADAPTER_REGISTRY 注册表 + fake 演示模式

04流式输出

📘 知识点
  • 体验关键指标是首 token 延迟（TTFT），不是总延迟——第一个字出现的时刻决定"卡不卡"
  • 技术：SSE（POST 也能流式）；把各家流式事件统一成自己的事件协议（start/delta/end/error），前端一套代码通吃
  • Agent 特有价值：流式让执行过程可见（"正在查询订单…"），不再黑箱转圈
⚠️ 注意事项
  • 不可撤回：已推送的内容收不回——重试/降级只在首个增量之前有效，之后只能报错终止
  • 断流要给用户明确反馈（错误事件），别静默挂起让人干等
  • 调试陷阱：浏览器 DevTools 对 POST-SSE 的 EventStream 面板显示空白是已知问题，不代表没数据
  • 统计信息（usage/延迟）挂在结束事件上带回，别在前端猜
llm-unify service.py 的 emitted 标志与五种类型化事件

05结构化输出

📘 知识点
  • 用 JSON Schema 定义输出契约（字段/类型/必填），让模型输出机器可解析的数据
  • 模型能力分三档：原生 schema（Responses 协议）→ json_mode（保语法不保字段）→ prompt 注入（全靠说服）
  • 修复循环：校验失败把错题详情喂回去让它自纠错——这是 Agent"自我修正"的最小形态
⚠️ 注意事项
  • 铁律：永远本地校验——上游说"保证 JSON"不算数；交付给下游的必须是"验过的数据"或"明确的错误"
  • Schema 写严：additionalProperties: false ＋ required 列全，模型最爱"发挥"多余字段
  • 容错解析要剥噪声（代码围栏、前后解释文字），但修复循环必须限次数——无限重试就是烧钱循环
  • 校验只管格式不管语义：字段值里照样能藏敏感信息/注入内容，重要场景加内容扫描
llm-unify structured.py：三档降级 + 限次修复循环 + 泄漏扫描

06工具调用（tool_calls）进阶主题

📘 知识点
  • Agent 的标志性能力：请求里声明工具清单（名字＋参数 Schema），模型返回"调用哪个工具＋什么参数"而不是文本
  • 流程：模型下指令 → 你执行 → 结果以 tool 角色喂回 → 模型继续决策
  • 与结构化输出的关系：前者交付数据，后者下达指令；共享同一套底层（Schema＋校验＋修复）
⚠️ 注意事项
  • 工具描述是给模型看的文档——写不清楚模型就不会用或滥用，值得像写 API 文档一样认真
  • 工具实现要幂等、有超时：模型可能重复调用同一工具，卡死的工具会卡死整个循环
  • 权限最小化＋危险操作加确认：注入的危害上限＝Agent 手里的权限上限
  • 警惕间接注入：工具返回的内容（网页、文件）同样不可信，别直接拼进上下文

07Agent Loop（核心循环）进阶主题

while 轮数 < 上限: 响应 = LLM(messages, tools) if 响应.tool_calls: 结果 = 执行(工具) messages += [assistant(tool_calls), tool(结果)] # 观察喂回 continue return 响应.content # 模型不再要工具 = 它认为完成了
📘 知识点
  • Agent 的定义性结构：思考 → 行动 → 观察 → 再思考，直到模型认为任务完成
  • 终止权在模型：它通过"是否继续要工具"表达任务是否完成，你的代码只是执行它的决定
  • 每一轮都是一次完整的 LLM 调用：计费、失败、观测都按轮数放大
⚠️ 注意事项
  • 必须设最大轮数上限——模型陷入"再查一下"的死循环时，烧的是你的钱
  • 别只信 finish_reason：模型说"完成"不代表真的完成，关键任务要有结果校验兜底
  • 每轮记录观测（request_id 串联整条轨迹），出问题能回放"它当时看到了什么"
  • 工具结果喂回时注意上下文膨胀——长输出先摘要再入列
案例未实现循环编排（课程下一层）；llm-unify 是循环的"供水系统"，保证每轮调用可靠

08Prompt 工程

📘 知识点
  • System Prompt 是 Agent 的行为契约，五要素：角色目标 / 行为约束 / 输出契约 / 示例(few-shot) / 异常处理
  • few-shot 用例子立标杆，远胜用形容词描述（"像示例那样"＞"要简洁专业"）
  • Prompt 即代码：版本号、只增不改、可 diff、可回滚
⚠️ 注意事项
  • 改一个词行为就漂移——没有版本管理的 prompt 调优全是玄学，出事连"昨晚改了啥"都不知道
  • 用户提交的模板要沙箱渲染（SSTI 攻击能逃逸到代码执行）；变量缺失立即报错，半成品 prompt 比报错危险
  • 改 prompt 要有评测基准对照——不然"感觉变好了"可能是错觉（详见主题 11）
  • 约束写在 system（高特权），不要写在容易被覆盖的位置
llm-unify prompts.py：版本不可变＋Jinja2 沙箱＋StrictUndefined

09安全（注入与防护）

📘 知识点
  • Prompt 注入是 OWASP LLM Top 1：指令与数据共用自然语言，没有语法边界（SQL 有参数化，prompt 没有银弹）
  • 现实解法是纵深防御（层层降险）：输入包裹标记＋输出泄漏扫描＋角色分层＋权限最小化
  • 第一性原理：注入的危害上限 ＝ Agent 手中的权限上限
⚠️ 注意事项
  • 不可信数据用显式标签包裹（如 <untrusted_data>）＋ system 里声明处置规则
  • 输出侧扫描系统提示词泄漏（被劫持的典型痕迹），命中即拒绝交付
  • 接工具之前先想最坏情况：会说话的模型被注入最多社死，会用工具的模型被注入就是事故
  • 安全策略集中在网关层做——业务方各自为战必有遗漏
llm-unify security.py 两道可配置防线（案例无工具，权限最小化暂不适用）

10工程骨架（稳定性与可观测）

📘 知识点
  • 稳定性三件套分工：限流管常态（令牌桶：允许突发、稳态收敛）、重试管瞬时故障（指数退避＋抖动防惊群）、熔断管持续故障（连败即跳过，快速失败）
  • 重试纪律：只重试瞬时错误（429/超时/5xx）；确定性错误（401/超窗）一次都别试，但可以换路由
  • 可观测：每个请求一个 request_id 贯穿全程；token/延迟/重试/降级/错误全部落库
⚠️ 注意事项
  • 429 要尊重 Retry-After，别按自己的节奏硬撞
  • 抖动别省——所有客户端同一毫秒集体重试会把刚恢复的上游再次打挂（惊群）
  • 失败请求也要落库——错误率统计的分母不能缺
  • 熔断/限流是进程内状态：多副本部署要换集中式实现（如 Redis）
llm-unify 整个骨架：rate_limit / retry / router / observability（Retry-After 采用列为已知差距）

11评测（Evals）进阶主题

📘 知识点
  • Agent 的行为 = prompt × 模型 × 参数 的乘积——任何一项变了行为就变，没有评测的调优是玄学
  • 评测三件：用例集（输入＋期望）→ 批量执行 → 判分（精确匹配 / 规则断言 / 结构校验 / LLM-as-judge 让另一个模型打分）
  • 三大用途：版本对比（prompt v1 vs v2）、模型对比（A 家 vs B 家）、回归（改完不退步）
⚠️ 注意事项
  • 先建评测、再改 prompt——不是改坏了才想起要基准
  • 用例输入要固定；模型是概率的——要么固定采样参数，要么多次采样取分布
  • LLM-as-judge 有偏差（位置偏好、长答偏好、自我偏好），重要结论要人工抽检
  • 评测集本身也是代码：要版本管理、要随能力演进更新
案例未含评测模块（课程后续主题）；79 个单测演示了"把行为钉死"的同一思想

12成本控制进阶主题

📘 知识点
  • 成本公式：（输入 token ＋ 输出 token）× 轮数 × 单价——输出通常比输入贵数倍，而 Agent Loop 按轮数放大一切
  • 四个抓手：模型分级（简单任务走便宜模型，路由解决）、上下文精简（记忆管理，见主题 02）、输出限长（max_tokens）、前缀缓存（prompt caching：重复前缀计费打折）
  • 前提是每次调用的成本可归集（request_id × usage 落库），否则优化无从下手
⚠️ 注意事项
  • 防死循环就是防账单爆炸——轮数上限是成本闸门，不只是稳定性闸门
  • max_tokens 两面性：既是成本闸门也是截断风险（结构化输出被截成非法 JSON，进修复循环反而更贵）
  • 前缀缓存要求前缀完全一致——system 放最前、模板少动、变量放后段
  • 便宜模型多出的重试/修复轮次，可能比贵模型一次到位更贵——按任务实测而不是看单价
llm-unify 已有成本归集（usage×单价落库）与模型分级路由；前缀缓存依赖上游能力，属接入层进阶
